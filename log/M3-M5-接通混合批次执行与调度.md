# 变更：M3–M5 接通混合批次执行与调度（已实现，待 GPU 验证）

## 1. 目标

将已经由 M1 表达、由 M2 正确提交的批次执行计划接入真实 mixed batch（同一批同时含 prefill 和 decode）运行路径：先让模型执行器能以一次前向计算处理两类请求，再让调度器正式产生这种计划。

本次不实现 mixed CUDA Graph、专用 mixed attention 内核或性能调优；这些都依赖后续 GPU 正确性与性能证据。

## 2. 范围

- `nanovllm/engine/model_runner.py`
  - `ModelRunner.prepare_prefill()`：确认既有变长元数据构造可直接表示 mixed 项。
  - `ModelRunner.run()`：mixed 计划改走 eager varlen attention（即时执行的变长注意力）路径。
- `nanovllm/engine/scheduler.py`
  - `Scheduler.schedule()`：先调度 running decode，再以剩余预算调度 waiting prefill，生成稳定的 mixed `SchedulerOutput`。

未修改 `BlockManager`、`Sequence`、attention 内核、LM head、CUDA Graph 捕获、采样和 postprocess（执行后提交）。

## 3. 修改前

```text
Scheduler.schedule()
    ↓
纯 prefill 计划；存在 prefill 时立即返回
或
纯 decode 计划
    ↓
ModelRunner.run()
    ↓
发现 prefill/decode 混合时抛出异常
```

`prepare_prefill()` 已按每个 `Sequence` 的 `num_cached_tokens` 与 `num_scheduled_tokens` 打包变长元数据，但混合计划在到达它之前就被拒绝。调度器也从未生成 mixed 计划。

## 4. 修改后

```text
Scheduler.schedule()
    ↓
decode（稳定 running 顺序）→ prefill（稳定 waiting 顺序）
    ↓
mixed SchedulerOutput
    ↓
ModelRunner.run()
    ↓
prepare_prefill() 的 varlen 元数据
    ↓
一次 eager varlen 模型前向
    ↓
M2 的逐请求采样与 postprocess
```

mixed 计划中，prefill 段的 `q_len` 为本轮提示词分块长度；decode 段的 `q_len = 1`。两者均满足：

```text
k_len = num_cached_tokens + num_scheduled_tokens
```

因此既有 `prepare_prefill()` 可生成同一 packed 输入所需的 positions、slot mapping、paged block tables 与 `cu_seqlens_q/k`。它在此表示“变长注意力元数据”，而非断言每个请求都是 prefill。

## 5. 关键差异

1. M3 没有引入新的 mixed 元数据包装函数。
   - 调查确认 `prepare_prefill()` 的计算仅依赖请求进度；decode 的 `num_scheduled_tokens = 1` 自然成为长度为 1 的 varlen 段。新增只转调的 helper 会制造无独立行为的接口，因此未保留。

2. `ModelRunner.run()` 用 `is_mixed` 与 `use_varlen` 选择执行路径。
   - 纯 prefill 与 mixed 计划走 `prepare_prefill()` 和 eager varlen attention；纯 decode 继续走 `prepare_decode()`、`flash_attn_with_kvcache` 与 CUDA Graph 快路径。

3. `Scheduler.schedule()` 改为 decode-first。
   - 每个 decode 消耗一个请求槽位和一个 token 预算；之后 waiting 队首 prefill 使用剩余预算。输出顺序固定为 decode 在前、prefill 在后。

4. 分块资格只由此前是否已有 prefill 决定。
   - 已经调度 decode 不会阻止 waiting 队首 prefill 分块；一旦已有 prefill，放不下的后续 waiting 请求必须停止，不能越过队首。

## 6. 架构决策

将 mixed 的执行选择放在 `ModelRunner.run()`，而不是修改 attention 或新增长期状态。调度器拥有本轮阶段与队列顺序，`Sequence` 拥有进度，runner 在执行边界将两者转换为已有 varlen 表达；职责没有重复。

decode-first 是延续中间生成请求的低 token 延迟策略。后到请求即使完成 prefill，也只追加到 `running` 队尾，不会插队到既有 decode 请求之前。代价是新 prefill 只能使用剩余资源，这是当前路线明确的服务策略。

不让纯 decode 复用 varlen 路径：虽然元数据正确，但会失去当前的 paged-KV decode 内核与 CUDA Graph 快路径。mixed 批因形状动态，先以 eager varlen 正确性为先。

## 7. 不变量

1. 每个计划项在一轮中最多出现一次，顺序为已选 decode 后接已选 prefill。
2. `len(scheduled)` 不超过 `max_num_seqs`，所有 `num_scheduled_tokens` 的总和不超过 `max_num_batched_tokens`。
3. waiting 队首是本轮唯一可分块的 prefill；后续请求不能绕过它。
4. 已选 decode 必须恢复到 `running` 队首的原始顺序；完成 prefill 仅追加到队尾，部分 prefill 留在 waiting。
5. mixed、纯 prefill 都走 varlen；纯 decode 保留原 CUDA Graph 路径。
6. 调度计划本身不推进 `num_cached_tokens`；只有 M2 的成功后处理才能提交进度与 token。

## 8. 发现与后续工作

- 本地未运行验证。M1–M5 仍需 GPU 证据，尤其要验证一次 mixed 前向、两类请求的 KV 写入、logits 对齐、M2 采样提交、前缀缓存、抢占及纯路径回归。
- `LLMEngine.step()` 的吞吐显示仍按批次级 `SchedulerOutput.is_prefill` 统计；decode-first mixed 计划会使其显示不能代表实际 mixed token 数，但不影响调度、模型输出或请求状态。该统计问题不纳入本次正确性里程碑。
- M6 将通过公开 engine 接口进行端到端兼容性验证，并仅根据实际 GPU 失败证据进行最小修复。
