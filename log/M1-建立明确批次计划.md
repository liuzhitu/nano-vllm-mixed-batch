# 变更：M1 建立明确批次计划（已实现，待 GPU 验证）

## 1. 目标

让 `Scheduler`（调度器）能够显式表达一个批次中每个请求本轮的执行阶段，而不再只返回请求列表和一个代表整个批次的 `is_prefill` 开关。

原实现隐含“一个批次只能全是预填充或全是解码”的假设，因此没有可靠的位置表达未来 mixed batch（混合批次：同一批同时有预填充和解码请求）。

本次只建立并传递批次执行计划；不实现实际的混合 GPU 执行、不改变调度策略，也不改变采样逻辑。

## 2. 范围

- `nanovllm/engine/scheduler.py`
  - `ScheduledSequence`：单个请求在本轮的计划项。
  - `SchedulerOutput`：整批执行计划。
  - `Scheduler.schedule()` 与 `Scheduler.postprocess()`。
- `nanovllm/engine/llm_engine.py`
  - `LLMEngine.step()`：整体传递执行计划。
- `nanovllm/engine/model_runner.py`
  - `ModelRunner.run()` 与 `warmup_model()`：接收新的计划接口。

未修改 `Sequence` 的跨进程序列化、KV Cache（注意力键和值缓存）块管理、注意力计算、采样器和真正的混合调度。

## 3. 修改前

```text
Scheduler.schedule()
    ↓
list[Sequence] + 批次级 is_prefill
    ↓
LLMEngine.step()
    ↓
ModelRunner.run(seqs, is_prefill)
    ↓
Scheduler.postprocess(seqs, token_ids, is_prefill)
```

`is_prefill` 与整个列表绑定。模型执行器和后处理都据此把整个批次走向同一种路径，因此无法表达“请求 A 本轮预填充、请求 B 本轮解码”。

## 4. 修改后

```text
Scheduler.schedule()
    ↓
SchedulerOutput
    ↓
list[ScheduledSequence(seq, is_prefill)]
    ↓
LLMEngine.step()
    ↓
ModelRunner.run(scheduler_output)
    ↓
Scheduler.postprocess(scheduler_output, token_ids)
```

调度器现在是执行计划的生产者：每个计划项将原始 `Sequence`（请求长期状态）与“本轮执行阶段”绑定。包装对象只属于本轮计划；调度器的 waiting/running 队列仍只持有 `Sequence`，不会被短期计划状态污染。

M1 期间，调度器仍只产生纯预填充或纯解码计划。`SchedulerOutput.is_prefill` 仅用于维持旧纯批路径；真正混合的计划会被 `ModelRunner` 显式拒绝。

## 5. 关键差异

1. `schedule()` 的返回值由 `(seqs, is_prefill)` 变为 `SchedulerOutput`。
   - 批次的“成员”和“每个成员如何执行”成为同一个接口契约（调用双方共同遵守的输入输出约定）。

2. `LLMEngine` 将同一份 `SchedulerOutput` 同时交给模型执行和后处理。
   - 执行前计划与执行后提交保持一一对应，避免中间层拆散请求列表和阶段信息。

3. `ModelRunner.run()` 接收计划对象，并在真实执行边界拒绝阶段混合的计划。
   - 当前模型输入构造仍只支持一种阶段；显式报错比静默选择其中一种路径更安全。

4. `postprocess()` 检查模型返回的 token 数是否与计划请求数相等。
   - 防止 `zip()` 在长度不一致时悄悄截断，造成部分请求未提交状态却不被发现。

## 6. 架构决策

将“本轮按 prefill 还是 decode 执行”的信息放在 `ScheduledSequence`，而不是让 `ModelRunner` 根据 `Sequence` 自行猜测。

原因：调度器已经拥有请求队列、KV 分配和本轮调度决策；它应是执行计划的唯一决策者。若模型执行器重新推断阶段，调度与执行会各自拥有一份决策逻辑，未来混合批次下容易产生不一致。

没有额外保存计划 token 数或采样资格：前者已有 `Sequence.num_scheduled_tokens` 作为唯一来源；后者属于 M2 的采样边界，应在真正采样时计算。

## 7. 不变量

1. `SchedulerOutput` 中每个请求在一轮调度中最多出现一次，并保持原有顺序。
2. `ScheduledSequence` 只描述本轮执行计划；`Sequence` 仍是请求长期状态的唯一来源。
3. 建立计划本身不提交计算进度；只有既有 `postprocess()` 在模型成功返回后更新请求状态。
4. M1 的纯预填充和纯解码路径保持原有语义。
5. 当前 `ModelRunner` 不得静默执行 mixed plan；遇到 prefill/decode 混合必须在执行前报错。

## 8. 发现与后续工作

- `SchedulerOutput.is_prefill` 仍是纯批兼容属性，取第一个计划项的阶段；真正 mixed execution 时不能再依赖它。
- M2 在采样器边界实现逐请求采样资格，避免未完成的预填充请求提前采样。
- M3/M4 需要让模型输入元数据与执行路径按计划项表达阶段，并执行真正的混合批次。
- M5 才允许调度器在同一轮选择 waiting 队列中的预填充请求和 running 队列中的解码请求。
- 本地仅完成静态语法检查与 diff 检查；尚未在 GPU 上验证纯 prefill、纯 decode、张量并行传递和 mixed-plan 拒绝行为。因此 M1 未完成验收。
