# nano-vLLM 代码变更日志

## 目的

在一次代码修改、一个里程碑（milestone，分阶段的小目标）或明确功能变更完成后，编写能长期恢复上下文的工程日志。

日志记录设计和运行语义，而不是复述 Git diff（代码差异）。它应回答：为什么改、修改前后系统如何运行、模块职责或接口契约（模块之间的输入输出约定）有什么变化、为什么采用当前设计，以及哪些不变量（任何运行时都必须成立的条件）不能破坏。

## 触发与边界

- 仅在创建或更新项目代码变更日志、完成里程碑工程记录，或用户明确要求写日志时调用本 skill。
- 代码尚未完成或尚未验证时，不预先创建空日志；可在已有计划中记录待办，但不把它写成完成日志。
- 里程碑完成记录仍写入 `docs/milestones/<里程碑标识>.md`，并保留 `nanovllm-milestone-development` 要求的固定章节；用本 skill 的内容要求充实其中的“工程记录”。
- 用户明确要求独立日志时，写入其指定位置；未指定时，优先沿用项目现有 `log/` 的命名方式。不要为了同一事实同时写两份近似内容，除非用户明确要求。

## 写作原则

- 用中文、短段落和分点；专业名词首次出现时附上简短解释。
- 记录需要思考才能重新得到的信息：设计理由、控制流（程序的执行路径）、数据流、状态转换、所有权、模块边界、隐藏假设。
- 不复制完整代码、完整 diff、无意义行号、纯格式变化、普通变量改名或机械性修改。完整代码历史由 Git 保存。
- 一个普通日志以约 1～2 页 Markdown 为宜，保留约 2～5 处真正关键的差异。
- 不属于当前里程碑的问题只记录为后续工作，不顺手扩展实现。

## 独立日志固定结构

除非日志嵌入既有里程碑模板，否则按下列结构撰写；某节没有内容时简短说明即可。

```markdown
# 变更：<名称>

## 1. 目标

## 2. 范围

## 3. 修改前

## 4. 修改后

## 5. 关键差异

## 6. 架构决策

## 7. 不变量

## 8. 发现与后续工作
```

### 1. 目标

简洁说明原系统为何不能满足需求、本次要实现什么、明确不解决什么。

### 2. 范围

列出真正涉及的文件、类、函数/方法与关键数据结构；不记录普通格式化或顺手调整的文件。

### 3. 修改前

用真实调用链说明原来的控制流、数据流、模块职责、隐藏假设和当前限制。例如：

```text
Scheduler
    ↓
list[Sequence]
    ↓
LLMEngine
    ↓
ModelRunner
```

重点回答：原来的设计为何不能自然支持这次需求？

### 4. 修改后

同样用调用链说明谁现在负责什么、数据结构多表达了什么、控制权或状态所有权是否移动、接口契约是否变化。不要只写“新增了某结构”。

### 5. 关键差异

只选 2～5 处改变系统语义的内容：接口变化、核心控制流变化或新增关键数据结构。必要时给少量 Before/After 代码片段，并解释其运行时含义；不要列出机械性修改。

### 6. 架构决策

说明为什么把职责放在当前模块、有哪些明显备选方案、为何未选它们。这一节优先保存代码本身难以推导的设计理由。

### 7. 不变量

写出简短、明确、可判断的条件，并说明负责方和破坏后的表现。例如：调度器是执行计划的唯一决策者；同一轮调度中一个请求只属于一个执行组；旧的纯预填充和纯解码路径保持语义不变。

### 8. 发现与后续工作

记录隐藏假设、潜在缺陷、架构限制和当前范围外的工作，说明影响与计划处理的后续里程碑。

## 推理系统日志的优先观察点

对本项目优先记录：控制流、数据流、请求或缓存的所有权、状态转换、调度决策、接口契约、执行计划、KV Cache（注意力缓存）或内存所有权、模块边界和隐藏假设。

## 写完后的自检

确认仅靠日志即可回答：

- 为什么做这次修改，范围是什么？
- 修改影响哪些核心模块？修改前后如何运行？
- 真正变化的系统语义和设计理由是什么？
- 后续开发不可破坏哪些不变量？
- 发现了什么尚未处理的问题？

若日志接近完整 diff，收缩为设计与语义；若必须重读整个代码库才能回答这些问题，则补足调用链、假设或决策理由。
