# Mixed batch 实现路线图

## 总目标

让一次 `LLMEngine.step()` 同时处理两类请求：

- 正在逐 token 生成的请求（decode，解码：每轮只算最新的一个 token）；
- 新到或尚未算完提示词的请求（prefill，预填充：一次计算提示词的一段或全部 token）。

这两类请求必须共用一次模型前向计算（模型根据输入计算输出的过程），随后分别正确更新 KV 缓存（保存历史 token 的注意力键和值）、采样并更新各自状态。

## 固定不变量

以下规则在所有里程碑中都不能被破坏：

- 调度到的 token 不等于已经算完的 token。只有模型成功执行、后处理成功提交后，才能推进已计算进度。
- `num_cached_tokens` 表示该请求中“已经连续算完并且 KV 缓存有效”的 token 数。
- 一个批次不能超过 `max_num_batched_tokens`（单批 token 上限）和 `max_num_seqs`（单批请求数上限）。同一请求在一批中只能出现一次，顺序必须稳定。
- 是否采样必须按请求判断。未完成的预填充只能写入 KV 缓存，不能生成新 token。
- 纯预填充、纯解码、前缀缓存（复用相同提示词前缀的 KV 缓存）、EOS（模型的结束标记）和 `max_tokens`（最大生成长度）必须继续可用。
- mixed batch 可以先走 eager varlen attention（即时执行的变长注意力路径）。纯解码的 CUDA Graph（提前录制 GPU 计算图以减少启动开销）快路径必须保留；mixed batch 的 CUDA Graph 优化暂不做。

## M1：建立明确的批次计划

### 要做什么

- 用 `SchedulerOutput`（调度器输出对象）替换当前 `(seqs, is_prefill)` 返回值。
- 批次中的每个请求都记录：
  - 对应的 `Sequence`（请求状态对象）；
  - 本轮属于预填充还是解码；
- 本轮计划 token 数继续只保存在已有的 `Sequence.num_scheduled_tokens` 中，不在批次计划中重复保存。
- 这个批次计划成为 scheduler、engine、model runner 和 postprocess（执行后的状态提交）之间唯一可信的传递对象，也要能传到张量并行的工作进程。

### 验收标准

- 本地实现阶段不新增或运行 CPU 测试。
- 后续上传到租用的 GPU 实例后，验证纯预填充和纯解码仍产生等价结果，并检查请求不重复、顺序稳定、阶段信息正确、token 和请求数统计正确。
- M1 在 GPU 验证完成前不得标记为完成。

## M2：按请求采样并提交结果

### 要做什么

- 在真正采样前，根据请求当前进度和批次计划中的阶段信息判断资格，再把采样结果准确映射回原请求。
- 对于尚未完成的预填充：
  - 写入 KV 缓存；
  - 推进已计算进度；
  - 不采样、不消耗随机数、不追加新 token。
- 后处理按请求独立提交状态，而不是使用“整个批次是否预填充”的判断。

### 验收标准

- 后续 GPU 实例测试同时放入一个部分预填充请求和一个可采样请求。
- 验证两者各自的进度、是否追加 token、采样结果对齐都正确，并确认纯预填充和纯解码不回归。

## M3：构造统一的 mixed batch 元数据

### 要做什么

让 `ModelRunner`（模型执行器）把不同类型请求打包成一份输入：

- 预填充请求：`q_len = 提示词分块长度`；
- 解码请求：`q_len = 1`；
- 每个请求：`k_len = num_cached_tokens + num_scheduled_tokens`。

同时按照稳定的批次顺序构造：

- positions（token 的位置编号）；
- slot mapping（每个新 KV token 写入缓存的槽位）；
- paged block tables（分页 KV 缓存的块编号表）；
- `cu_seqlens_q` 和 `cu_seqlens_k`（变长注意力中每个请求 query/key 边界的累积长度表）。

纯解码当前的元数据和 CUDA Graph 路径不改。

### 验收标准

- 针对“一个预填充 + 一个解码”的元数据检查通过。
- 覆盖可复用前缀缓存时的 block table。
- GPU 验证打包后的 tensor（张量）形状和值正确。

## M4：验证一次联合模型执行

### 要做什么

- 人工构造一个 mixed `SchedulerOutput`，不先修改正式调度策略。
- 让它走现有的变长注意力路径，在一次模型前向计算内完成。
- 只要批中含有预填充，就走变长注意力；纯解码继续走当前的 `flash_attn_with_kvcache` 和 CUDA Graph 快路径。

### 验收标准

- GPU 检查确认只进行了一个前向计算。
- 预填充和解码请求的 KV 缓存都写入正确。
- 每个请求都有一行对应的最终 logits（模型对下一 token 的原始分数）。
- 采样结果与批次计划中的请求顺序一致。

### 暂不改的部分

- 默认不修改 attention 或 LM head（输出词表分数的最后一层）。
- 只有 GPU 证据证明现有变长注意力无法表达“`q_len = 1` 的解码请求 + 分页 KV 缓存”时，才另开里程碑改它们。

## M5：正式启用 mixed 调度

### 要做什么

- 修改 `Scheduler.schedule()`：
  1. 先按稳定队列顺序加入正在运行的解码请求；
  2. 再用剩余的请求数和 token 预算加入 waiting 队列中的预填充请求。
- waiting 队首的长提示词可以使用剩余预算分块处理。
- 后面的 waiting 请求不能绕过队首请求。
- 现有 KV 块分配、抢占和所有权规则先保持不变；若发现明确的正确性问题，再单独立项处理。

### 验收标准

- 后续 GPU 实例测试覆盖：
  - 一个解码请求 + 一个新预填充请求；
  - 一个解码请求 + 一个被分块的预填充请求；
  - 两种全局上限；
  - 请求唯一性和顺序；
  - 队列状态变化；
  - KV 块分配与抢占；
  - 纯预填充和纯解码兼容性。

## M6：端到端兼容性验证

### 要做什么

- 通过公开的 engine 接口运行 mixed 请求。
- 将每个请求的结果与该请求单独执行时的结果对比。
- 在受控采样条件下验证输出一致性。
- 覆盖 EOS、`max_tokens`、提示词分块、前缀缓存复用、KV 释放，以及纯路径不回归。

### 验收标准

- 明确报告已经通过的 GPU 正确性检查。
- 上传 GPU 实例前，必须写清楚未验证项、原因和后续 GPU 测试方案。
- 完成后写入工程记录，并明确哪些性能优化仍被推迟。

## 暂缓事项

- mixed batch 的 CUDA Graph 捕获和性能调优。
- 多 GPU 场景的专门 mixed batch 优化。
- 改变前缀缓存策略。
- 与 mixed batch 正确性无关的调度、内存管理或模型重构。
