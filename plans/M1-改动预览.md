## M1 目标

把当前调度器返回的：

```python
(seqs, is_prefill)
```

改为明确的 `SchedulerOutput`（调度器输出对象）。该对象逐请求记录：

- 对应的 `Sequence`（请求状态对象）；
- 本轮属于预填充还是解码；
- 本轮计划 token 数继续只保存在已有的 `Sequence.num_scheduled_tokens` 中，不在批次计划中重复保存。

M1 只建立和传递这份批次计划。当前的纯预填充批、纯解码批，以及实际的模型执行行为都保持不变。

## 运行路径

```text
LLMEngine.step()
  ├─ Scheduler.schedule()
  │   └─ 当前返回 (seqs, is_prefill)
  ├─ ModelRunner.run(seqs, is_prefill)
  │   └─ 根据整个批次的 is_prefill 选择预填充或解码路径
  └─ Scheduler.postprocess(seqs, token_ids, is_prefill)
      └─ 根据整个批次的 is_prefill 决定是否追加采样 token
```

对应代码位置：

- `nanovllm/engine/scheduler.py`：调度请求、维护队列和 KV 块（保存历史注意力键和值的缓存块）。
- `nanovllm/engine/llm_engine.py`：串接调度、模型执行和执行后的状态提交。
- `nanovllm/engine/model_runner.py`：执行模型，并向张量并行工作进程传递调用参数。
- `nanovllm/engine/sequence.py`：保存单个请求的 token、KV 进度和跨进程传输状态。

## 调查发现

### 当前阻塞点

当前的 `is_prefill` 同时承担三种不同含义：

1. 调度结果中“整个批次”的阶段；
2. `Sequence.is_prefill` 中“该请求跨进程传输时是否需要完整 token 列表”的序列化开关；
3. `Context.is_prefill` 中“attention（注意力计算）使用哪条 GPU 路径”的执行开关。

这使 mixed batch（同批同时包含预填充和解码请求）没有地方可靠表达“每个请求本轮的真实阶段”。

### 跨进程传递限制

`Sequence.__getstate__()` 对 decode 请求只传递 `last_token`（最新 token），对 prefill 请求传递完整 token 列表。这是已有的传输优化，M1 不改它。

因此，调度阶段不能只依赖 worker 进程中的 `Sequence` 内容来反推请求阶段；阶段信息必须由批次计划显式携带。

### 验证安排

- 仓库目前没有 `tests/` 目录，也没有 pytest 配置。
- 根据用户当前决定，M1 不新增或运行 CPU 测试。
- M1 的行为验证统一推迟到后续租用的 GPU 实例上执行。
- 在 GPU 验证完成前，M1 只能报告“已实现、待验证”，不能标记为完成。

## 设计方案

在 `scheduler.py` 新增两个数据对象：

```text
ScheduledSequence（单个请求的调度项）
  - seq：Sequence 请求对象
  - is_prefill：本轮是否为预填充

SchedulerOutput（整个批次的调度结果）
  - scheduled：按稳定顺序排列的 ScheduledSequence 列表
  - seqs：兼容性访问属性，返回所有 Sequence
  - is_prefill：M1 纯批兼容用的阶段访问属性
```

M2 将在真正调用 sampler（采样器）前，根据 `Sequence` 当前进度和 `ScheduledSequence.is_prefill` 临时计算采样资格，实现“部分预填充不消耗随机数”。

## 计划修改的文件

| 文件 | 当前职责 | M1 的最小修改 |
|---|---|---|
| `nanovllm/engine/scheduler.py` | 选择请求、维护队列和 KV 块、执行后提交状态 | 新增批次计划数据对象；`schedule()` 返回 `SchedulerOutput`；`postprocess()` 接收该对象，但仍按纯批兼容路径执行。 |
| `nanovllm/engine/llm_engine.py` | 串接调度、模型执行和后处理 | `step()` 从批次计划读取序列、统计值和阶段信息，并整体转发该对象。 |
| `nanovllm/engine/model_runner.py` | 模型执行和张量并行进程通信 | `run()` 接收 `SchedulerOutput`；M1 内仍只允许同质批次（全部预填充或全部解码），并从计划读取兼容阶段信息；`warmup_model()` 构造纯预填充计划。 |

## 明确不修改的部分

- `nanovllm/engine/sequence.py`：保留当前序列化优化。
- `nanovllm/engine/block_manager.py`：不改 KV 块分配、释放、哈希或抢占。
- `nanovllm/utils/context.py`、`nanovllm/layers/attention.py`、`nanovllm/layers/embed_head.py`：不改 GPU 元数据、注意力计算或 logits（下一 token 的原始分数）选择。
- 调度策略不变：waiting 队列仍优先于 running 队列；M5 才启用 mixed 调度。
- sampler（采样器）行为不变；M2 才在采样前临时判断资格并做选择性采样。
- 不创建 `docs/milestones/` 工程记录；只有 M1 实现并验证完成后才创建。

## 修改前后对比

```text
修改前

Scheduler.schedule()
  → (seqs, is_prefill)
       │
       ├─ 模型执行：整个批次只能是 prefill 或 decode
       └─ 后处理：整个批次共用一个采样判断


M1 修改后

Scheduler.schedule()
  → SchedulerOutput
       └─ scheduled（稳定顺序）
            ├─ {seq A, prefill}
            └─ {seq B, prefill}

M1 期间仍只生成纯预填充或纯解码批。
M2 才在采样前判断资格；M5 才允许预填充和解码同批。
```

## M1 不变量

- `SchedulerOutput` 中每个请求最多出现一次，顺序与原 `seqs` 一致。
- 本轮计划 token 数只有 `Sequence.num_scheduled_tokens` 一份来源，且总量不超过原调度预算。
- 建立计划不推进 `num_cached_tokens`；只有既有的 `postprocess()` 成功后才推进。
- 当前纯预填充与纯解码结果保持兼容。
- 若计划项中同时出现预填充和解码，`ModelRunner` 在执行前必须显式报错，不能静默选择一种纯路径。
